# 三调用面架构梳理与重组方案

> 目标：把「CLI（给 AI Agent）/ Web 控制台（给人）/ 独立 Python 脚本」三种调用方式，从「各自重写逻辑」整理成「共用一个核心 + 三个薄适配层」，并建立一个机制来应对你后面加功能时**各面进度不一**的现实。

---

## 0. 一句话结论

**有交叉，而且交叉得很重。** 真正的共用核心只有 4 个模块（`boss_firefox` 爬虫 / `boss_state` 持久化 / `boss_replier` LLM 文本 / `boss_automation` 投递+聊天），但它们被三个调用面以**不一致的方式**复用：CLI 是干净的 HTTP 客户端，Web 控制台和独立脚本却**各写了一遍采集和分析**。重组的本质 = 抽出一个 `core/`，让三个面都当它的适配器。

还有一个隐藏但致命的约束：**浏览器是互斥单例**（Web 控制台和 match_report 不能同时开 Firefox profile）。这决定了「谁有资格直接驱动浏览器」——只能有一个常驻进程当浏览器 owner。

---

## 1. 现状：三个调用面的真实代码关系（带证据）

| 调用面 | 入口 | 怎么复用核心 | 关键点 |
|--------|------|--------------|--------|
| **Web 控制台** | `boss_app.py`（FastAPI :8010，51 路由） | `from boss_automation import BossAutomation`<br>`from boss_state import ...`<br>`from boss_replier import generate_greeting` | 路由层**自己重写**了采集（`search_jobs` :1433 / `scan_current_page` :1662）和单 JD 分析（`analyze_jd` :1750，内联 LLM prompt）。**不直接 import `boss_firefox`/`match_report`**，爬虫经 `BossAutomation` 间接用 |
| **CLI（给 Agent）** | `lakejob_cli/`（cli.py + client.py + schema.json） | `import httpx` → 调 `boss_app` 的 HTTP API | **最干净的一面**：纯 HTTP 客户端，本地零领域逻辑。命令数 20、schema 14（与 README 16/18 对不上，见旧盘点） |
| **独立脚本** | `match_report.py` | `from boss_firefox import BossScraper`<br>`from boss_state import ...` | **平行实现**：自己写 `collect` + `build_report`/`analyze_match`，**不 import `boss_app` 也不 import `boss_automation`**。等于绕开 Web 控制台另搞了一套 |

共享但被不同方式复用的底层模块：
- `boss_firefox`（BossScraper）：被 `match_report` **直接**用、被 `boss_automation` **直接**用；Web 控制台经 `boss_automation` 间接用。
- `boss_state`（SQLite）：被四个面共用。
- `boss_replier`：`generate_greeting`（Web 招呼语）、`generate_reply`（自动化聊天 + 匹配分析）。
- `boss_automation`：Web 控制台 import；**`match_report` 完全不用** → 投递/聊天监控目前是 Web 独占能力。

非三面的旁支：`boss_company.py`（smart-send 的 helper，路由没挂 → 死链）、`interview/`（完全独立子服务）、`scripts/refine_search_kw.py`（一次性维护，直接碰 `boss_state`）。

## 2. 交叉点诊断

### 2.1 真·共用核心（保留，无需动）
`boss_firefox` / `boss_state` / `boss_replier` / `boss_automation` —— 跨面复用，方向也对（底层被上层依赖）。

### 2.2 重复实现债（必须合并，这是重组的主战场）
| 能力 | Web 控制台实现 | 独立脚本实现 | 后果 |
|------|---------------|-------------|------|
| **岗位采集** | `boss_app.search_jobs` / `scan_current_page`（路由层） | `match_report.collect` | 两份采集逻辑，修 bug 要改两处；且脚本独立开浏览器，触发互斥 |
| **单 JD 匹配分析** | `boss_app.analyze_jd`（:1750 内联 prompt） | `match_report.analyze_match` | 两份 LLM 分析，输出格式可能漂移 |
| **市场报告 / 简历优化 / 话术** | Web 有 `optimize-resume` `chat-suggestion` 端点 | 脚本有 `build_report` | 能力只落在一面，另一面没有 |

> 一句话：**CLI 没问题；Web 和脚本是「同一个大脑写了两遍」。** 重组就是把这两遍收口到 `core/`。

### 2.3 浏览器互斥约束（架构级，不是代码细节）
采集/投递/聊天都靠 `BossScraper` 开同一个 Firefox profile。事实约束（见项目记忆）：**Web 控制台和 match_report 不能同时跑**。
→ 推论：**浏览器 owner 只能有一个常驻进程**（= Web 控制台）。CLI 和脚本都不该自己开浏览器，而应委托给运行中的 Web 控制台。**所以「独立脚本」若要保持为一种调用方式，正确形态是「脚本调 Web API」，而非「脚本自己开浏览器」**——否则互斥规则永远解不开。

## 3. 目标架构：六边形 / 端口-适配器

```
                ┌─────────────────────────────────────────────┐
   调用面(适配器) │  Web 控制台        CLI(Agent)      独立脚本   │
                │  boss_app.py   →  lakejob_cli  →  match_report │
                │  (浏览器 owner)   (HTTP客户端)    (调 core 批处理)│
                └───────────────┬──────────┬──────────┬────────┘
                                │ 都只依赖 │ 都只依赖 │ 都只依赖
                ┌───────────────▼──────────▼──────────▼────────┐
   共享核心 core/  │  scrape │ store │ reply │ act │ analyze │ report │
                │ (浏览器单例) (SQLite) (LLM) (投递+聊天) (匹配) (报告)│
                └───────────────────────────────────────────────┘
                                  │
                          boss_company(helper) / interview(独立子服务) / scripts(维护)
```

**依赖方向铁律：适配器 → 核心，核心不反向依赖任何适配器。** 今天 `boss_app` 把采集写在路由层、破坏了这规则；收口后路由只做「参数校验 + 调 core + 拼响应」。

### 3.1 建议目录结构
```
lakejobai-job-radar/
├── core/                  # 共享领域核心（无调用面耦合）
│   ├── scrape.py          # 封装 BossScraper（浏览器单例入口）
│   ├── store.py           # = boss_state，SQLite 持久化
│   ├── reply.py           # = boss_replier，LLM 文本
│   ├── act.py             # = boss_automation，投递 + 聊天监控
│   ├── analyze.py         # 单 JD 匹配分析（统一 1 份）
│   ├── report.py          # 市场报告生成（统一 1 份）
│   └── capabilities.py    # ★ 能力注册表（进度追踪，见 §4）
├── surfaces/
│   ├── web/               # boss_app.py → FastAPI 路由，只调 core
│   ├── cli/               # lakejob_cli → HTTP 客户端（保留现状）
│   └── script/            # match_report.py → import core 跑批（不再自开浏览器）
├── interview/             # 独立子服务（保留）
├── scripts/              # 一次性维护脚本
└── docs/
```
> 不要求一次性大搬家。可以先在 `core/` 里新建模块、把逻辑迁进去，三个面改成 import core；原文件可逐步废弃。

## 4. 解决「各面进度不一」：能力注册表（capabilities.py）

你后面加功能，必然出现「Web 先做、CLI 下周接、脚本先不做」。**用一个 `CAPABILITIES` 注册表当唯一真相源**，每个面从它动态生成自己的命令/菜单：未实现的面自动显示「未支持 / coming soon」，而不是散落在三处 if-else。

```python
# core/capabilities.py
@dataclass
class Capability:
    key: str
    title: str
    surfaces: set[str]          # 已实现并暴露给哪些调用面
    requires_browser: bool = False   # 是否要走浏览器 owner(Web 控制台)
    status: str = "ready"        # ready | beta | planned | broken

CAPABILITIES = {
    "collect":         Capability("collect", "采集岗位", {"web","cli","script"}, requires_browser=True),
    "match_analyze":   Capability("match_analyze", "JD 匹配分析", {"web","cli","script"}),
    "market_report":   Capability("market_report", "市场报告", {"script"}),         # 还没接 Web/CLI
    "auto_apply":      Capability("auto_apply", "自动投递", {"web","cli"}),
    "chat_auto_reply": Capability("chat_auto_reply","AI 自动回复", {"web","cli"}),
    "company_preview": Capability("company_preview","公司画像预览", set()),         # 全缺 → 当前死链
    "smart_send":      Capability("smart_send", "智能投递", set()),                # 全缺
}
```
- **Web 控制台**：从注册表生成侧边栏/按钮，缺的面灰掉。
- **CLI（Agent）**：`schema.json` 由注册表**生成**，不再手搓 14 条还和代码对不上；Agent 调未实现能力直接拿到明确报错而非 404。
- **脚本**：只 import 它 `surfaces` 含 `"script"` 的能力。
- **新功能上线流程**：① 在 `core/` 写实现 → ② 在注册表加一条、填 `surfaces` → ③ 各面按需接。进度一目了然。

## 5. 分阶段重组建议（按杠杆/风险排序）

| 阶段 | 动作 | 风险 | 收益 |
|------|------|------|------|
| **P0** | 建 `core/capabilities.py` 注册表 + 用它能生成 CLI `schema.json` | 低 | 立刻消除「文档/代码对不上」，新功能进度可追踪 |
| **P1** | 抽 `core/analyze.py`、`core/report.py`，Web 的 `analyze_jd` 与脚本 `analyze_match`/`build_report` 都改调它 | 中 | 消灭两份分析逻辑的漂移 |
| **P2** | 抽 `core/scrape.py` 收口浏览器单例；`match_report` 改为「调 Web API 或 import core 但不自开浏览器」 | 中 | 解除互斥死结，脚本真正变成第三种调用方式 |
| **P3** | 挂上 `company_preview` / `smart_send` 两个死链路由（或从注册表移除，别再骗 Agent） | 低 | 要么可用、要么不暴露 |
| **P4** | 目录归拢到 `surfaces/{web,cli,script}`（可最后做，纯搬运） | 低 | 结构清爽，但非必须 |

## 6. 给你的决策点

1. **「独立脚本」的定位**：是接受它「调 Web API、自己不开浏览器」（推荐，解互斥），还是保留「离线独立开浏览器」的批处理模式（那就要和 Web 控制台错峰、且接受两份采集逻辑共存）？
2. **先从哪步动手**：我建议 P0（能力注册表）性价比最高、零破坏，能立刻让 CLI schema 不再说谎。要我直接建 `core/capabilities.py` 并接管 `schema.json` 生成吗？
3. **目录大搬家（P4）要不要现在做**：它不解决功能问题，只是整洁度；建议功能收口后再搬。
