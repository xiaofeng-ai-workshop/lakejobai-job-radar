## 1. 背景与决策

### 1.1 为什么要重组

现有代码存在三类问题，导致维护成本高、调用面混乱：

- **调用面交叉脏**：Web 控制台（`boss_app.py`）和独立脚本（`match_report.py`）各自重写了一套采集 + 分析逻辑，属于重复实现债。CLI 是干净的 HTTP 客户端，但三面对同一能力的实现不统一。
- **文档严重漂移**：命令数 README 写 18、SKILL 写 16、schema 14、代码实际 20；两份 changelog 冗余；升级方案混在已交付文档里。
- **结构问题**：`boss_app.py` 是 fat monolith（51 路由一文件）；`smart_send` / `company_preview` 死链（CLI 宣称、后端无路由）；`boss_geo.py` 无人引用。

### 1.2 已确认决策

| 决策 | 内容 |
|------|------|
| ① 脚本不开浏览器 | 批处理 / 定时任务统一走 Web API，不再本地直连 `boss_firefox`。 |
| ② 目录大搬家延后 | `surfaces/{web,cli}` 归拢、FastAPI 分层等功能收口后再做（见 §4.5 / P5）。 |
| ③ 不设独立脚本适配器 | 批处理只是 CLI 的"脚本模式"，不是第三调用面；`match_report.py` 废弃，能力下沉 `core/`。 |
| ④ 已采纳补充项 | 浏览器并发锁、SQLite WAL、配置统一、测试基线、版本号单一来源——全部并入对应阶段（见 §6）。 |
| ⑤ 死链选 A 下架 | 从能力注册表移除 `smart_send` / `company_preview`，CLI schema / `client.py` 同步删除。 |

### 1.3 进度

- **文档树结构（§5.2）已确认定稿**（2026-09-10）。
- **P0 已完成**（见 §6 与 §9）；P1–P4 待口令推进；P5 功能收口后。

## 2. 核心原则（三条铁律）

1. **适配器只依赖核心，核心不反向依赖任何适配器。** `core/` 不知道有 Web / CLI 的存在。
2. **浏览器（Firefox profile）单例归 Web 控制台独占。** CLI（含脚本模式）绝不自己开浏览器，浏览器操作一律委托运行中的 Web 控制台（经 API）。
3. **能力注册表 = 唯一真相源。** 命令清单 / API 路由 / 菜单都从 `core/capabilities.py` 派生，禁止在 README / SKILL / schema 三处手搓导致漂移。

## 3. 功能架构：能力清单

功能按"用户能做什么（能力）"而非"哪个 py 文件"划分，每条标注暴露面。

### 3.1 能力矩阵（最终版，14 条）

| 域 | 能力 key | 标题 | 暴露面 | 浏览器 |
|----|----------|------|--------|--------|
| 采集 | `collect` | 采集岗位 | web / cli | 是 |
| 分析 | `match_analyze` | 单 JD 匹配分析 | web / cli | 否 |
| 分析 | `market_report` | 市场报告(md) | cli（批处理模式）/ web（待接） | 否 |
| 分析 | `resume_optimize` | 简历优化建议 | web / cli | 否 |
| 分析 | `chat_suggestion` | 沟通话术建议 | web / cli | 否 |
| 行动 | `auto_apply` | 自动/批量投递 | web / cli | 是 |
| 行动 | `chat_auto_reply` | AI 自动回复+聊天监控 | web / cli | 是 |
| 行动 | `smart_send` | 智能投递 | **无（死链，下架 A）** | 是 |
| 数据 | `shortlist` | 候选池管理 | web / cli | 否 |
| 数据 | `company_query` | 公司/已投递查询 | web / cli | 否 |
| 数据 | `company_preview` | 公司画像预览 | **无（死链，下架 A）** | 否 |
| 配置 | `settings` | 设置(CORS/Key/城市) | web（cli 用 env） | 否 |
| 系统 | `system` | 启停/心跳/重登 | web / cli(status) | 是 |
| 独立 | `interview` | 面试刷题子服务 | 独立进程 | 否 |

> **两点说明**
> - 全表只有 **web / cli 两个调用面**，无第三"脚本调用面"。批处理 / 定时只是 CLI 的"脚本模式"。
> - `market_report` 当前由 `match_report.py` 独家实现；该脚本已确认废弃（决策③），报告逻辑下沉 `core/report.py`，由 `lakejob batch market-report`（CLI 脚本模式）调用。Web 未来可复用同份逻辑。生成报告时内部调用 `core/analyze.py`，但该分析不单独暴露为 CLI 命令。

### 3.2 域说明："系统"与"独立"

- **系统**：Web 控制台进程的生命周期操作——启停服务、心跳保活、重新登录。`system` 通常需确认浏览器状态，故标"需浏览器上下文"。
- **独立**：`interview/` 面试刷题子服务，独立 FastAPI 进程，不共用浏览器与 SQLite，不列入两调用面矩阵。

### 3.3 死链能力说明与处置（已选 A 下架）

- **`company_preview`（公司画像预览）**：投递前看公司整体情况——规模、已投递 HR、活跃岗位、职级分布，辅助决策。
- **`smart_send`（智能投递）**：对公司下所有岗位，自动挑职级最高 / 最活跃的 HR 只投一次，避免同公司多岗位重复沟通。

**现状**：`boss_company.py` 写了辅助函数、单测也在，但 `boss_app.py` 没挂路由 → CLI 里 `company-preview` / `smart-send` 调过去 404。属半成品。

**处置（决策⑤ = A 下架）**：从能力注册表移除两条目，CLI `client.py` 与 `schema.json` 同步删除对应段；前端 `dashboard.html` 本就无这俩按钮（已核实），无 UI 影响。后续若要真正可用，再补路由（属新增功能，不在本次范围）。

## 4. 技术架构：core + 两适配器

### 4.1 共享核心 `core/`（无调用面耦合）

| 模块 | 职责 | 当前来源 |
|------|------|----------|
| `core/scrape.py` | 封装 BossScraper，**浏览器单例唯一入口** | boss_firefox |
| `core/store.py` | SQLite 持久化 / 去重 / 候选池 | boss_state |
| `core/reply.py` | LLM 文本（招呼语 / 回复 / 分析 prompt） | boss_replier |
| `core/act.py` | 投递 + 聊天监控（驱动浏览器） | boss_automation |
| `core/analyze.py` | 单 JD 匹配分析（统一 1 份） | boss_app.analyze_jd + match_report.analyze_match 合并 |
| `core/report.py` | 市场报告生成（统一 1 份） | match_report.build_report |
| `core/capabilities.py` | 能力注册表（唯一真相源，新建） | — |

### 4.2 两个适配器 + CLI 双模式（只依赖 core）

| 适配器 | 角色 | 调用方式 |
|--------|------|----------|
| **web** (`boss_app.py`) | 浏览器 owner + API server | 直接 import core；浏览器操作经 `core/act.py` + `core/scrape.py` |
| **cli** (`lakejob_cli/`) | 通用 API 客户端（人 / Agent / 脚本共用） | `httpx` → Web API（现状即如此，保持） |

**CLI 的两种使用模式（不是两个适配器）**

| 模式 | 触发 | 举例 | 本地逻辑 |
|------|------|------|----------|
| 交互模式（默认） | 人 / Agent 实时输入 | `lakejob collect --city 武汉` | 无，纯透传 API 结果 |
| 脚本模式 | 定时 / 批处理 | `lakejob batch market-report`、cron、`automation_update` | 仅本地**非浏览器**逻辑：调 API 拿数据后 import `core/report.py` 生成报告（读 SQLite，不开浏览器） |

**为什么脚本不是独立适配器**：① CLI 与脚本架构上同一件事——都是 HTTP 客户端调 Web API；② 多一个调用面 = 多一份能力矩阵 / 命令注册 / 文档维护，会重演 README/SKILL/schema 三处漂移；③ "批处理"是调用方式（非交互、长运行、本地产物），不是新能力集合。

**`match_report.py` 废弃路径（决策③）**
- 报告生成 → `core/report.py`（吸收 `match_report.build_report`）
- 采集 → 改走 `lakejob collect`（CLI 调 Web API），不再自带 `boss_firefox`
- 单 JD 分析（内部步骤）→ `core/analyze.py`
- 入口 → `lakejob batch market-report`；老的 `match_report.py` 删除
- `scripts/`（如 `refine_search_kw.py` 一次性清洗）保持独立，靠 `python -m scripts.xxx` 或 cron 跑，不纳入适配器

### 4.3 依赖方向（铁律 1/2 的可视化）

```
web ──┐
      │
cli ──┼──> core/（scrape 单例 / store / reply / act / analyze / report / capabilities）
(含脚本模式)
      │
      ▲ core.act/scrape 只在 web 进程内被真正执行（浏览器 owner）
      │ cli（含脚本模式）的浏览器需求 → 经 Web API 委托
core 不 import 任何适配器；适配器互不 import
```

### 4.4 文件重构映射

**会变（核心逻辑抽出 / 适配器瘦身）**
- `boss_firefox.py` → `core/scrape.py`；`boss_state.py` → `core/store.py`；`boss_replier.py` → `core/reply.py`；`boss_automation.py` → `core/act.py`
- `boss_app.py` 的 `analyze_jd` 实现 + `match_report.analyze_match` → 合并 `core/analyze.py`
- `match_report.build_report` → `core/report.py`
- `boss_app.py` → 路由层保留，业务逻辑下沉 `core/`

**确认废弃（决策③）**：`match_report.py` 删除，迁移路径见 §4.2。

**基本保持原样**
- `lakejob_cli/`：已是纯 HTTP 客户端，只改 schema 由注册表生成 + 新增 `batch` 子命令壳
- `interview/`：独立子服务，完全不动
- `scripts/`：一次性维护脚本，保持独立

**建议清理**：`boss_geo.py` 无人引用，P5 大搬家时顺手删。

### 4.5 目标代码树（P5，含 FastAPI 分层）

> 目录大搬家在功能收口后做（决策②）。先画出目标结构，避免"FastAPI 路由重构后的目录树"缺失。

```
lakejobai-job-radar/
├── pyproject.toml
├── requirements.txt
├── README.md                 # 顶层薄入口
├── surfaces/                 # 调用面（P5 新建）
│   ├── web/                  # FastAPI 应用
│   │   ├── main.py           # FastAPI 工厂 + 生命周期 + 静态文件挂载
│   │   ├── routers/          # 按域拆分的路由（APIRouter）
│   │   │   ├── __init__.py
│   │   │   ├── jobs.py       # /api/jobs/*（采集、扫描、投递）
│   │   │   ├── analyze.py    # /api/jobs/analyze
│   │   │   ├── apply.py      # /api/jobs/apply*, /api/companies/*
│   │   │   ├── chat.py       # /api/conversations/*, 自动回复
│   │   │   ├── settings.py   # /api/settings/*
│   │   │   └── system.py     # /api/status, /api/system/*, /api/doctor
│   │   ├── deps.py           # 公共依赖：DB、浏览器单例、AI client、操作锁
│   │   └── static/dashboard.html
│   └── cli/                  # 原 lakejob_cli/
│       ├── __main__.py / cli.py / client.py
│       ├── schema.json       # 由 capabilities.py 生成
│       └── scripts/market_report.py   # 原 match_report 市场报告能力
├── core/                     # 共享核心（P0-P2 抽）
│   ├── capabilities.py       # P0 能力注册表
│   ├── scrape.py / store.py / reply.py / act.py
│   ├── analyze.py / report.py
├── scripts/                  # 一次性维护脚本（保持独立）
├── interview/                # 独立子服务（不动）
├── tests/                    # 回归测试（P0-P1 补）
├── reports/                  # 报告输出目录
└── docs/                     # 文档树（P4 归拢，见 §5.2）
```

**FastAPI 分层收益**：路由按域拆分不再 51 路由塞一文件；`deps.py` 统一管理浏览器锁 / DB / AI client，便于 mock 与并发控制；所有 `/api/*` 路径保持不变，终端用户无感知；未来可单 router 拆服务而不影响其他路由。

## 7. 风险清单

架构重组不新增对 Boss 的操作，但抽层 / 改调用链 / 下架能力会引入以下风险：

| 风险 | 阶段 | 影响 | 缓解措施 |
|------|------|------|----------|
| **Boss 封号风险** | P2 后潜在放大 | 脚本 / CLI 改走 Web API，若批处理任务未加频率控制，可能短时间集中操作浏览器被风控识别为异常 | 浏览器操作锁强制串行；采集 / 投递加随机间隔（3-10s）；每日投递上限可配置；操作日志完整记录 |
| **浏览器并发冲突** | P2 | Web 手动与 CLI / 脚本同时驱动同一 Firefox profile，点击错位、状态污染 | P2 实现浏览器操作锁，覆盖 search/apply/apply-batch/scan/scan-and-apply/fetch-details/sync/send/open-conversation/heartbeat/navigate-chat 共 11 个浏览器操作；CLI 提交任务若锁忙则收到 409 busy |
| **SQLite 写冲突 / 损坏** | P1 | Web 常驻写、CLI 读、`scripts` 一次性写并发，触发 `database is locked` 或更严重损坏 | P1 开启 WAL + 单写者；明确"写只走 Web" |
| **API / 输出行为漂移** | P1 | `analyze` / `report` 抽到 core 后格式或字段名变化，导致前端 / CLI 解析失败或报告样式不一致 | P1 加回归测试 + 输出物 diff；保持 JSON / markdown schema 不变 |
| **死链下架遗漏** | P3 | `client.py` / `schema.json` / 前端按钮没删干净，用户仍能看到入口但点进去报错 | P3 下架时 grep 全项目扫描 `smart_send` / `company_preview`；UI 回归确认 |
| **配置来源不一致** | P0/P3 | CLI 读 env、Web 读表，同一配置项两边值不同导致行为混乱 | 统一以 `settings` 表为权威；env 仅用于启动注入 |
| **版本号继续漂移** | P4 | README / SKILL / 后端版本各自为政 | P4 以 `pyproject.toml` 为唯一来源，文档由脚本读取生成 |
| **测试覆盖不足** | P0-P1 | 抽层后无单测，改坏未发现 | P0 起补 `core/capabilities` 单测；P1 补 `analyze` / `report` 回归测试 |
| **P5 目录大搬家破坏导入** | P5 | `surfaces/` 改名后旧导入路径失效 | P5 批量替换 + 全量 import 检查 + 跑测试 |

> 关于 Boss 封号：重组本身不是封号根因，**真正触发风控的是操作频率 / 模式**。重组后脚本走 Web API，若不在 Web 层加统一频率控制，反而可能因多调用面同时提交任务放大风险——故浏览器锁 + 统一限流必须和 P2 一起做。
